# 0006 — sweeper-finalised sessions close with `end_reason="error"`, not `"user_abandoned"`

**Phase:** 1 (Task 1.1)

## The gap

Task 1.1 says: on the 90s resume-grace sweeper finalising an abandoned runtime, "mark the
session `closed` with `end_reason = user_abandoned`." But `sessions.end_reason` is a
CHECK-constrained column (Phase 0, `services/api/app/models/session.py`):

```python
SESSION_END_REASONS = (
    "user_hangup", "duration_reached", "persona_concluded",
    "budget_exhausted", "distress_exit", "error",
)
```

`"user_abandoned"` is not in that set. Writing it would violate `ck_sessions_end_reason` and
raise at the exact moment a disconnected session is being cleaned up — the one path that must
not itself fail.

## Decision

The sweeper's finalize path closes the session with `end_reason="error"` for now — the closest
existing value for "this session did not end through any of the five specific, named paths."
The explicit `end_session` message (a deliberate user hangup) still closes with
`end_reason="user_hangup"`, which was already correct and needed no change.

## Why not just widen the CHECK constraint

That's the right eventual fix, but it's a real migration (CLAUDE.md §5: "Migrations are
Alembic, always reviewed, never autogenerated-and-committed blind"), and Phase 0's schema
wasn't written with Phase 1's exact vocabulary in mind — reasonable, since `docs/04-state-
machine.md` didn't exist yet when it was built (see `docs/decisions/0001`). Silently smuggling
a new enum value through application code instead of a migration is worse than the temporary
imprecision of collapsing it into `"error"`.

## Follow-up

Add `"user_abandoned"` to `SESSION_END_REASONS` in a real migration, and switch the sweeper's
finalize path to use it, once this repository's next schema-touching phase runs. Until then,
distinguishing "the client vanished" from "something actually broke" requires looking at the
`session_finalized` log line's `end_reason`/`turns` fields, not the DB row alone.
